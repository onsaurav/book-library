## Dependency check (rule 1b)

Everything below depends on requirements that are `agreed` with no code yet —
expected for a repository whose `src/` is still empty. Two dependencies need a
specific note:

- **REQ-BOOK-003 depends on REQ-BOOK-001**, which is refused above. REQ-BOOK-001's
  *structure* (one card per Book, cards in a grid, empty-library state, newest
  first) is fully specified by its acceptance criteria and is not touched by the
  open styling question — only colour, font and layout polish are. This plan
  therefore builds the card markup and the gallery loop as part of REQ-BOOK-003's
  own scope, but no test below carries `@covers REQ-BOOK-001` or
  `@covers REQ-BOOK-002` — those stay unclaimed until those two requirements are
  agreed, even though the same file ends up satisfying their acceptance criteria
  too. Re-run `/feature-plan` on them once open to add the missing annotations
  rather than writing new code.
- **REQ-BOOK-008 depends on REQ-BOOK-012** (the SQLite store), which is `agreed`
  but unplanned. This slice implements only the two store operations REQ-BOOK-008
  needs (`addBook`, `listBooks`) behind an interface designed so REQ-BOOK-012's
  own plan (restart survival, second-tab visibility, delete) can extend it
  without changing the shape callers already depend on.

## What must be true

**REQ-BOOK-003** — Each book card carries a Delete control for that Book
- A book card in the gallery displays a Delete control.
- Three Books in the Library produce three Delete controls, one per card.
- The Delete control can be reached and activated with the keyboard alone, and
  carries an accessible label (e.g. "Delete {book title}", not a bare icon).

**REQ-BOOK-004** — The home page carries a button labelled "+ Add Book"
- The home page always renders a button whose visible label is exactly
  "+ Add Book".
- The button is present whether the Library holds Books or not.
- When the Library is empty, an empty-library message is shown alongside it.

**REQ-BOOK-005** — Activating "+ Add Book" opens a modal form over the home page
- Activating the button displays a modal form above the page; the URL does not
  change.
- On successful submission the modal closes itself and the new Book is visible
  behind it.
- The modal can be closed without submitting, via a Close/Cancel control or
  Escape.
- Every modal control is keyboard-reachable and carries an appropriate label
  (focus moves into the modal on open and returns to the trigger on close).

**REQ-BOOK-006** — The modal form provides an input for each detail of the Book
- Inputs exist for Name, Author, Language and Price, plus a submit control.
- No Book ID input exists — the application assigns it.
- The Name input is labelled for the book's title.
- Language is a free-text input, not a select/list.
- Price accepts a BDT amount with up to two decimals and rejects negative
  input at the field level.
- Name and Author accept non-Latin script (e.g. Bangla) without corruption.

**REQ-BOOK-007** — The modal form refuses a submission that fails validation
- Submitting with Name, Author, Language or Price blank creates no Book, and
  the form names the field at fault.
- Submitting a Price that is not a valid number, or is negative, creates no
  Book.
- Validation runs again on the server, not only in the browser.
- A failed add shows a clear, visible error message in the form.

**REQ-BOOK-008** — Submitting the modal form adds exactly one Book to the Library
- A valid submission increases the Library by exactly one Book, and every
  stored field equals what was entered.
- The application assigns the Book ID; the client never supplies one.
- A duplicate Name+Author pair is allowed — both Books exist.
- The Book is written to the server-side SQLite store, shared by every user of
  the application (no per-user Library).
- A store failure surfaces as a visible error message, not a silent no-op.
- Concurrent submissions are not required to be guarded against.
- No edit path exists — correcting a Book means deleting and re-adding it.

## Approach

Framework choice is genuinely open: REQ-BOOK-014/016 (Node version, web
framework, port, build step) are both still `draft`, and REQ-BOOK-015 (dependency
policy) is too. Building against an assumed framework risks a rewrite the moment
the client answers. This plan uses **Node's built-in `http` module and no
front-end framework or bundler** — the one choice that is a strict subset of
every possible answer to those three open questions, and needs no dependency at
all. If the client later approves a framework, only `src/server.js` and the
route wiring change; the modules below do not.

Per the coding-style rule for `src/`, everything the application serves — HTML,
CSS, client JS — lives under `src/`, not a root-level `public/`.

```
src/
  server.js                 Bootstraps http.createServer, routes /api/books,
                             serves src/public/ as static files.
  routes/
    books.js                GET /api/books, POST /api/books. (DELETE is
                             REQ-BOOK-010's, not this slice.)
  store/
    bookStore.js             listBooks(), addBook(details) -> Book. Wraps
                             SQLite behind an interface with no driver-specific
                             shape, so the driver (built-in node:sqlite vs. a
                             package) can be chosen later without touching
                             callers — see "Decisions this forces".
  validation/
    bookValidation.js        validateBookDetails(details) -> { valid, errors }.
                             Same module used by the server route (REQ-BOOK-007)
                             and re-run client-side for inline field errors
                             (REQ-BOOK-006/007) — one rule set, not two.
  public/
    index.html                Page shell: gallery container, "+ Add Book"
                             button, a <template> for the modal.
    styles.css                 Layout and spacing only. No branding/colour
                             decisions — REQ-BOOK-001/002's open question.
    app.js                     Boot: fetches /api/books, renders the gallery,
                             wires the "+ Add Book" button.
    gallery.js                  Renders one card per Book (id, name, author,
                             language, price, Delete control) and the
                             empty-library state. Structural only — see the
                             REQ-BOOK-001/002 note above.
    modal.js                   Open/close, focus trap, focus return, Escape
                             and Cancel handling.
    addBookForm.js              Builds the four inputs + submit control, runs
                             client-side validation via bookValidation.js,
                             submits to POST /api/books, surfaces field and
                             submission errors, closes the modal on success.
```

## Decisions this forces

- **No web framework, plain `http`.** Follows from REQ-BOOK-014/016/015 all
  being open; documented above as the minimal-risk default, not a considered
  choice between alternatives — so no ADR yet. If the client's answer makes a
  framework the actual choice, that becomes an ADR at that point, not this one.
- **SQLite driver.** REQ-BOOK-012 fixed "SQLite"; it did not fix *how* Node
  talks to it. `node:sqlite` (built-in, but experimental and Node-version-gated)
  vs. a package such as `better-sqlite3` is a real decision with real
  alternatives, blocked on REQ-BOOK-014/016 naming a Node version. `bookStore.js`
  is written to the interface above precisely so this can be decided later as
  its own ADR without moving the call sites in `routes/books.js`.
- **Shared client/server validation module.** Not obviously required by any
  single acceptance criterion, but REQ-BOOK-007 requires server-side validation
  regardless of what the browser did, and REQ-BOOK-006 wants inline field
  errors — one `bookValidation.js` avoids the rule drifting between two
  implementations. Worth a line in an ADR once written, not before.

## What I am unsure about

- **Accessible label wording** for the Delete control ("Delete {title}" vs. a
  generic "Delete") isn't specified anywhere; the REQ-BOOK-003 test above checks
  only that a label naming the Book exists, not its exact text.
- **Where server-side validation errors surface** — REQ-BOOK-007 says "the form
  displays a message naming the field," but that criterion was written against
  the *client-side* check. Whether a server-rejected submission (bypassing the
  browser) gets the same per-field message or a generic one is not stated; the
  test skeleton above treats the server-validation criterion and the
  field-naming criterion as separate, unmerged tests until that's confirmed.
- **REQ-BOOK-001/002's eventual card markup** may still change once their
  styling question is answered (extra wrapper elements, cover-image slot, etc).
  `gallery.js` as scoped here covers only what REQ-BOOK-002's *content*
  criteria already fixed (which five fields, ID not user-typed, Name-as-title,
  free-text Language, BDT price) — not layout. Re-reading `gallery.js` once
  REQ-BOOK-001/002 close is expected, not a sign this plan was wrong.
