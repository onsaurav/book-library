# Plan — REQ-BOOK-009@v1

## Dependency check (rule 1b)

`depends_on: REQ-BOOK-008, REQ-BOOK-001`.

- **REQ-BOOK-008** is `verified` — built, tested, on this branch already.
- **REQ-BOOK-001** is still `draft`, blocked on the same open styling question
  as before ("what makes the interface modern/clean/attractive"). As with
  REQ-BOOK-003 in the last slice: that ambiguity is cosmetic, not structural.
  It doesn't touch whether a card renders or how the gallery updates — only how
  it looks. REQ-BOOK-009's three criteria are all about *timing* (no reload,
  the count goes up, the modal gets out of the way) — none of them are about
  appearance. Proceeding on that basis, same as last time; no test below
  claims `@covers REQ-BOOK-001`.

## What must be true

- A valid submission's new Book is visible in the gallery immediately —
  without the user reloading the page.
- If the Library held two Books before the submission, the gallery shows
  three book cards after it.
- The modal closes by itself, and the new Book is visible once it does —
  both parts of the same flow, not just one or the other.

## Approach

**No new source file.** This is very likely already built: `src/public/app.js`'s
`onSubmitted` handler (written while building REQ-BOOK-008) already does exactly
this —

```js
onSubmitted(book) {
  books = [book, ...books];
  renderGallery(books, galleryContainer, templates);
  modal.close();
}
```

— a client-side re-render with no navigation, immediately on success. Two of
REQ-BOOK-009's three criteria are arguably already exercised by tests written
for REQ-BOOK-005 and REQ-BOOK-008 (`add-book-submission.spec.js`), just not
under REQ-BOOK-009's own annotation — and the "two Books before, three after"
criterion isn't tested by anything yet.

Rather than relabel the existing REQ-BOOK-005/008 tests, this plan adds three
new tests to the existing `tests/book/add-book-submission.spec.js`, each
proving REQ-BOOK-009's own wording specifically. Some overlap with what's
already proven for 005/008 is expected and intentional — REQ-BOOK-009 owns the
"this all happens together, immediately, without a reload" guarantee, which is
a distinct claim from either half alone.

If it turns out the existing behavior doesn't actually satisfy one of these
(unlikely, but the point of writing the test is to find out), the fix is a
one-line change to `app.js`, not a new module.

## Test skeleton

```
tests/book/add-book-submission.spec.js  (additions)

  // @covers REQ-BOOK-009@v1
  test('a new Book is visible in the gallery without the page being reloaded')
    // Fill and submit the form; assert the card is visible; assert
    // page.url() / navigation did not occur (no reload happened).

  // @covers REQ-BOOK-009@v1
  test('the Library going from two Books to three is reflected in the gallery')
    // Seed the store with two Books before the page loads (server.store.addBook
    // x2, same pattern as gallery-delete-control.spec.js). Assert two cards are
    // shown before submitting, then three after.

  // @covers REQ-BOOK-009@v1
  test('the modal closes and the new Book is visible in the same flow')
    // Fill and submit the form; assert BOTH the dialog is hidden AND the new
    // card is visible, in one test, rather than the two facts proven
    // separately elsewhere.
```

## Decisions this forces

None. No new module, no new dependency, no storage or framework question
touched.

## What I am unsure about

- Whether "without the user reloading the page" needs an explicit assertion
  that no navigation occurred (e.g. checking `page.url()` is unchanged and no
  `load` event fired), or whether "the card appears without the test having to
  reload" is sufficient proof by construction. I've written the first test to
  check both the card's appearance and the absence of navigation, which is a
  slightly stronger claim than REQ-BOOK-005's "does not navigate away" test
  already makes for the button click — worth a second look at whether that's
  redundant or genuinely a separate guarantee for the submit action specifically.
- As with the last slice: if REQ-BOOK-001's eventual resolution changes the
  card markup, these tests (which locate cards by `.book-card` and visible
  text) should keep working, but that's an assumption, not a guarantee.
